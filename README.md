查询校园宿舍电表的**剩余电量、已用电量、已购电量**，拉取**每一笔充值记录**（精确到秒），
按充值账号做备注、按人汇总、导出 Excel / Markdown，支持**定时日报**与**充值到账提醒**，
并自带一个 Web 控制台：选楼栋房间、按时间范围查询、备注管理、导出、手动推送。

> 仓库里不含任何个人数据：没有写死房间号、群号、QQ 号或昵称。
> 房间由使用时从平台拉取的列表里选，推送目标由插件运行时向机器人查询得到。

## 一、它是怎么工作的（原理）

### 1. 数据来源

学校使用的是一套第三方「宿舍电表缴费」平台（前端为 H5 页面，后端为统一网关）。
该平台对每个房间以一串内部编码定位，而不是房间号本身。插件并不模拟人工点击页面，
而是直接按平台自己的协议去调用它的查询接口——因此速度很快，也不需要浏览器。

### 2. 请求协议（三层）

平台把每个请求都包装成同一种信封：

| 字段 | 含义 |
| --- | --- |
| `appid` / `appsecret` | 平台下发给前端的应用标识（前端代码里可见） |
| `biz_data` | 业务参数，**用 RSA 公钥加密后**再放进信封 |
| `biz_encryption` | 固定 `RSA` |
| `sign` | **MD5 签名**：把信封字段按 key 排序后拼上 `appsecret`，取大写摘要 |
| `timestamp` / `requestid` | 毫秒时间戳与随机请求号 |

也就是说：**业务参数先加密，整封信再签名**。

关于密钥来源，如实说明：`APPID`、`APPSECRET`，以及 `elec_core.py` 里那一对
**RSA 公钥 + 私钥**，全部来自该缴费平台自己的**微信小程序前端包**。小程序把它们
打包进了客户端，任何安装者本地都能提取出来——这是该平台前端的既有设计，不是本
插件另配的凭据。插件只是复刻小程序原本的请求/响应流程：

- **公钥**：加密发出去的 `biz_data`；
- **私钥**：解密平台返回的 `biz_data`（服务端用同一对密钥，所以客户端也带着私钥）。

这一对密钥只用于**这一个公开电费接口的信封加解密**，与用户账号、微信登录态、校园
统一身份认证都无关；插件不读取、不保存任何登录凭据。若平台轮换密钥，插件会失效，
届时需要按新版小程序前端重新提取。

### 3. 房间定位

平台内部用「楼栋编号 + 房间编号」定位，其中房间编号 = **楼栋号 + 房间号** 拼接。
插件会拉取全校房间清单并缓存（控制台里点「查询」即刷新），你只需要从下拉里选：

- **楼栋**：如「1 号楼」「2 号楼」…
- **房间**：该楼栋下真实存在的房号

插件自动换算成平台内部编号，**不需要填任何内部 ID**。
配置项里虽然仍保留 `楼栋号 / 房间号` 两个纯数字字段（便于脚本化部署），
但正常用法是在控制台里点「查询」后从列表选择——**手填容易填到平台查不到的房间**。

### 4. 余额是怎么算出来的

平台只返回两个累计值：**累计已用电量** 与 **累计已购电量**，
剩余电量 = 已购 − 已用。插件不做估算，直接照此计算。
「预计可用天数」则用「上一次记录的用电量差 ÷ 距上次的天数」推算，属于估算值。

### 5. 「已用电量 / 已购电量」怎么算

平台**只给一个累计读数**，没有历史明细接口（`/room/get` 只返回 `elecUsed` / `elecBuy` 两个数，
`/recharge/list` 才给充值台账）。所以区间数据有两条路子：

**① 电表读数做基线（精确）**——本地 `hist.json` 每天记一次读数。
默认开始时间那天有读数，就用「当前累计 − 基线」，算出这段区间真实用了多少。

**② 充值台账反推（区间跨度大时用这个）**——控制台三张卡默认走这条：
```
区间购电 = 区间充值金额 ÷ 固定电价
区间用电 = 区间购电 − 当前余额        （假定区间起点余额为 0）
已用比例 = 区间用电 ÷ 区间购电
```
固定电价在配置项 `elec_price` 里改，默认 **0.55 元/度**。
区间起点取自「默认开始时间」，卡片下方小字会写明：
`自 <区间起点> 起 · 按 <电价> 元/度 由 N 笔充值（合计 X 元）推算`。

> 为什么用充值反推：电表只给「此刻的累计数值」，没有「某天的数值」；
> 而充值记录能追溯到开户以来每一笔，所以跨度再大也算得出来。
> 前提是「区间起点余额为 0」——宿舍开学开户时表底为 0，这个假设对整学期成立；
> 如果账户里本来就有历史余额（比如上一届留下的），算出来的用电量会略微偏低。
> 结果缓存 180 秒，避免每刷一次首页都拉 200 多条充值记录。

**③ 全部已用电量**：平台返回的累计值，不做换算。这张卡片下面还会显示**今日用量**
（今天第一次记录的读数到现在这一段），是真实增量。

日报里的「累计用电 / 累计购电」仍跟默认开始时间走。

### 6. 充值记录的「人」是什么

平台在充值记录里**只提供一个买家内部编号**，不返回姓名、手机号或任何可识别信息。
插件把这个编号当作账号展示，并允许你**自己给每个编号起备注名**；
之后所有表格、通知都会同时显示「编号 + 备注名」，方便辨认。
备注只保存在本地数据目录，不会回传平台。

### 7. 通知是怎么发出去的

插件通过 OneBot 协议的聊天机器人接口发送消息。
推送目标用统一的 UMO 字符串表示：`平台:消息类型:会话号`，
例如 `default:GroupMessage:SESSION_ID`。
在 Web 控制台里可以直接从机器人已加入的群 / 好友列表中勾选，**无需手写该字符串**
（该输入框已从界面移除，只剩勾选）。

## 二、安装

1. 把整个插件文件夹放进 AstrBot 的插件目录（`data/plugins/` 下）。
2. 重启或重载插件。
3. 打开 AstrBot 管理面板 → 插件 → **无锡科技职业技术学院宿舍电费查询** →
   打开「电费控制台」页面，点「查询」选楼栋与房间，保存即可。

> 依赖：`cryptography`（加解密）、`openpyxl`（导出 Excel）。
> AstrBot 自带的运行环境通常已包含；若缺失，插件只会影响导出功能，其余功能不受影响。

## 四、Web 控制台

打开插件页面「电费控制台」，从上到下七块：

### 1. 当前房间

五张卡片：**剩余电量 / 已用电量 / 已购电量（两者均按默认开始时间）/ 已用比例 / 全部已用电量（附今日用量）**。
没有更早基线时，前三张会明确写「平台只给累计读数，缺 X 当天的读数，这段区间算不出」，不会拿累计值冒充分段值。
剩余电量低于阈值会变色提示。

### 2. 用电趋势

一张柱状图，右上角三个按钮切换范围：**过去 24 小时**（默认，每小时一根）、**近 7 天**、**近 30 天**（每天一根）。

- 数值取平台返回的**累计用电量**，相邻两次采样相减得到区间真实用电——充值不会让曲线跳变，也不需要拿充值记录对账。
- 采样随每次查询房间顺带完成，**4 分钟节流一次**，落在 `samples.json` 里保留 35 天；刚启用时小时柱需要一点时间积累，没有采样的时段显示为灰点。
- **近 7 天与近 30 天装上就能看**：优先用已有的每日记录（每天第一次与最后一次读数之差）回填。
- 卡片标题右侧显示所选范围的**合计与峰值**；鼠标悬停在柱子上可以看到具体时段与度数。

### 3. 房间设置

这一块**默认收起**，点标题展开、再点收起。

- 最左边是 **「查询」按钮**：点一下从平台拉取可选的楼栋与房间，填进两个下拉框（缓存 5 分钟）。
- **楼栋、房间只能从下拉里选**，不能手输——从源头上避免填到查不到的房间。
- 选好点「保存房间」，立刻按新房间重新解析并刷新首页数据。
- 界面上不再出现「小区 / 校区 ID」与「数据源」这类内部参数，插件用固定默认值处理。

### 4. 通知设置

这一块**默认收起**，点标题展开、再点收起。

- 每日推送时间（逗号分隔，24 小时制）、低电量阈值、充值监控间隔；
- 推送目标按 **群聊（N）** 与 **私聊（M）** 分行显示，条数在行首，
  名字多时自动换行并与名字区左对齐，不会挤成一团；
- 「检测可用会话」重新探测群聊与私聊；
- 两个开关：启用定时推送、启用充值监控；
- 提示语：*通知只发到选中的目标；未选中则不主动发送通知。*
  留空则该机器人的群列表会自动列出；选定后保存即可。

### 5. 充值记录查询

- 最左 **「默认开始时间」按钮**：弹窗选时刻，确认后每次打开控制台都从该时刻开始查；
  旁边的「开始时间」输入框照样能临时手改，只影响当前这一次。
- 开始 / 结束时间输入框按需收窄（210px），年份不再被挤成 `yyyy` 占位。
- 结束时间留空 = 自动取到最新。
- 右侧三个快捷键：**本周 / 近30天 / 开学至今**。
- 操作栏：导出 Excel、导出 Markdown、推送日报、推送充值提醒、刷新数据
  （有未同步改动时「刷新数据」会变橙色带圆点）。

### 6. 三个视图

**每人总金额表** / **充值明细表（总表）** / **个人充值记录**。
表格里可直接改备注（失焦即保存），表格与通知都会带上备注列。

备注输入框右边有个小眼睛 👁：**睁眼显示备注名，闭眼显示原始账号**（闭眼时输入框只读，
再点一次恢复编辑）。查别人的账又不想暴露备注时用它。

### 7. 运行日志

页面最下面一块，**默认收起**，点标题展开。用来回答两个问题：通知到底发出去没有、插件运行时报了什么。

- **插件日志**：进程内保留本插件最近若干条日志，四个按钮切换 **全部 / 正常 / 警告 / 错误**。
  选「全部」时，异常级别的条目直接列出，**正常**级别折成一行「正常 N 条（点击展开）」，
  点开才逐条显示；点「正常」按钮则完整列出该级别。每条带时间、级别、内容与源码行号。
- **已发送通知**：每一次推送的时间、类型（日报 / 充值记录 / 充值提醒）、成功与失败的目标数，
  点一下展开，能看到当时发出去的完整正文。这部分**落盘保存**（`notices.json`），重启后仍可查；
  日志本身只在进程内保留，重启后从新开始。

右上角「刷新」重新拉取。两个列表都只读，不改动任何数据。

## 五、推送预览

推送前一律先预览，确认后才真正发送。

### 日报

- 可改标题；可勾选要显示的项目：剩余电量 / 昨天用电 / 累计用电与购电 / 可用天数预测 /
  本月已充金额 / 低电量提醒。
- 累计用电、累计购电**不再附带任何括号说明文字**，就是干净的两行数字。
- 金额与电量来自服务端实时查询，预览里改不了。

### 充值提醒

固定格式如下（标题行带充值日期，时间只到秒）：

```
💰 充值提醒    YYYY-MM-DD
💵 充值金额：XX.XX 元
🕐 充值时间：HH:MM:SS
👤 充值账号：备注 XXXXX
🧾 充值订单号：XXXXXXXX
🏠 充值房间：X号楼 XXXX室
🔋 电量剩余：XXX.XX 度
```

预览弹窗里可以：

- 按账号粗筛（全不勾 = 全部）；
- **逐条勾选要推送哪几条**，带「全选 / 全不选」；
- **列表按充值时间倒序**（最新在最前），一次最多展开 **10 条**，超出部分会在标题旁注明
  「另有 N 条未展开」——但**合并消息与推送范围仍然是全部选中记录**，不受 10 条限制；
- 点 **「选中最近一次充值」**：按**最新那一天**取记录，把当天**所有人**的充值一次性选中。
  当天记录超过 10 条时列表只显示前 10 条，推送时按整天重算，不会漏；
- 勾 **「合并成一条消息发送」** 把选中的多条合成一条发出，避免刷屏；
- 直接在预览里改备注名，改完即时重算预览。

关闭预览（点遮罩、✕ 或取消）会立刻停止这次预览：已经在路上的请求回来后直接丢弃，
不会再往弹窗里写内容。

金额、时间、订单号来自服务端实时数据，不可修改。

**合并成一条时**的模板（头部只出现一次，每笔只留金额 / 时间 / 订单号）：

```
💰 某某的充值记录
🕐YYYY.MM.DD~至今

💵 充值金额：XX.XX 元
🕐 充值时间：YYYY.MM.DD HH:MM:SS
🧾 充值订单号：XXXXXXXX

💵 充值金额：XX.XX 元
🕐 充值时间：YYYY.MM.DD HH:MM:SS
🧾 充值订单号：XXXXXXXX
```

**「最近一次充值」那天**推全部人的模板（账号行只出现一次，同一人多笔连着列）：

```
💰 最近充值记录
🕐YYYY.MM.DD

👤 充值账号：备注一
💵 充值金额：XX.XX 元
🕐 充值时间：YYYY.MM.DD HH:MM:SS
🧾 充值订单号：XXXXXXXX

👤 充值账号：备注二
💵 充值金额：XX.XX 元
🕐 充值时间：YYYY.MM.DD HH:MM:SS
🧾 充值订单号：XXXXXXXX
```

## 六、通知

- **定时日报**：默认每天 08:00 与 20:00，可在设置里改成任意时刻（逗号分隔）。
- **充值到账提醒**：后台每隔若干秒比对一次充值记录，发现新记录立刻推送，
  内容包括金额、精确到秒的时间、充值账号（含备注）、以及当前剩余电量。
- 消息里显示哪些字段（剩余/昨天用电/累计/预计天数/本月充值/低电提醒）都可单独开关。
- 推送目标一个都没勾时不主动发送，不会乱发到默认会话。

## 七、配置项与「两边同步」

插件配置页（面板里的表单）和控制台改的是**同一批配置键**：

| 键 | 含义 |
| --- | --- |
| `loudong_no` / `room_no` | 楼栋号 / 房间号（建议在控制台选，别手填） |
| `notify_enable` / `notify_times` / `notify_targets` | 定时推送开关、时刻、目标 |
| `recharge_watch` / `recharge_interval` | 充值监控开关与间隔（秒） |
| `low_threshold` | 低电量阈值（度） |
| `elec_price` | 固定电价（元/度，默认 0.55），用于充值台账反推度数 |
| `default_start` | 默认开始时间 |
| `show_left` `show_delta` `show_total` `show_forecast` `show_recharge` `show_warn` | 日报显示项 |
| `napcat_url` / `napcat_token` | NapCat HTTP 地址与令牌（可选） |

共 17 项。**同步机制**：AstrBot 面板保存配置只写文件，而插件读的是内存副本。
插件在每次查询、保存、后台调度前都会检查配置文件 mtime，发现变化就重新载入。所以：

- 在面板改配置 → 最多若干秒内生效，**不需要重载插件**；
- 在控制台保存 → 先同步面板的最新改动再写入，**不会覆盖面板里刚改过的值**；
- 控制台顶部的设置项在保存后会重新拉一次 `overview`，面板里看到的就是最新值。

## 八、数据存放

插件只在自己的数据目录下写六类文件，不修改任何外部脚本或系统配置：

```
plugin_data/astrbot_plugin_wxsc_elec_bill/
├── notes.json        充值账号的备注
├── state.json        上次推送时的电量与已推送的充值记录号（用于去重）
├── hist.json         每日电量历史（用于「昨天用电」「全部已用」等基线，保留 120 天）
├── notices.json      已发送通知的记录（控制台「运行日志」可查，保留最近 200 条）
├── samples.json      趋势采样点（随查询记录累计用电量，4 分钟节流，保留 35 天）
└── export/           导出的 Excel / Markdown
```

删除该目录即可完全重置插件状态（备注、历史与去重基线会一并清空）。

## 九、并发模型（v3.0.0 上架审查整改）

v3.0.0 的功能与 v2.3.0 完全一致，改动集中在**线程模型**：把同步阻塞的网络调用
彻底移出事件循环。这一节说明为什么改、怎么改，以及如何验证。

### 1. 问题在哪

`elec_core.call()` 用的是 `urllib.request.urlopen`（同步阻塞），而 `_room()` 在缓存
未命中时会触发一次「拉全校房间清单」的网络请求。旧版有若干处在协程里**直接同步
求值** `self._room()`，包括把它当成 `asyncio.to_thread(ec.query_room, self._room())`
的实参——**实参在进入线程之前就已经在事件循环里算完了**，等于没有放进线程。
冷启动、或刚改完房间配置的那一次调用，会把整个 AstrBot 事件循环卡住十几秒，
影响同一时刻所有其他插件的响应。

### 2. v3.0.0 的改法

- **阻塞方法全部进线程**：`_room` / `_room_json` / `_balance` / `_room_tree` /
  `_report_text` / `_napcat_call` / `_napcat_base` 在协程里一律通过
  `await asyncio.to_thread(...)` 调用。
- **整块下沉，而不是逐个包**：首屏 `overview` 收拢成单个同步函数 `_overview_sync()`，
  一次线程调用取全量数据；`/电费` 指令与充值监控同理（`_elec_text()`）。
  这样不会出现「外层协程里先算了一半」的漏洞。
- **`_where()` 改为不触网**：只读房间缓存，未命中就用配置拼「X号楼 XXXX室（未校验）」，
  绝不为了显示一个名字去发网络请求。
- **双检锁**：`_room()` 用 `threading.Lock` 双检，多个请求同时冷启动也只拉一次清单。
- **启动预热**：`initialize()` 起一个 `_warmup()` 任务，3 秒后在线程里预取房间，
  第一次交互直接命中缓存。

### 3. 去掉子进程与提权依赖

旧版用 `subprocess.run(["sudo", "-n", "docker", "inspect", "napcat", ...])` 自动
发现 NapCat 容器 IP。v3.0.0 删除该逻辑，改为纯 HTTP 探测候选地址（配置项 →
环境变量 `NAPCAT_URL` / `NAPCAT_HTTP` → `127.0.0.1:3000` / `3001` /
`host.docker.internal:3000`），不再执行任何子进程，也不需要 sudo。

### 4. 清死代码与收紧超时

- 未被任何代码调用的 `_upload_file`（内部硬编码 `/app/napcat/plugins/elec-out/`
  容器路径）已删除。
- 网络超时从 25 秒降到 15 秒，最坏情况下占用工作线程的时间更短。

### 5. 怎么验证

- **静态**：自检脚本用 AST 遍历全部异步函数，只要协程体内出现未包 `to_thread`
  的阻塞调用就报错（`elec_core` 里的纯计算函数 `describe` / `summarize` /
  `parse_range` / `in_range` / `loudong_number` 除外）。当前 **21 个异步函数全部通过**。
- **运行时**：stub 掉 AstrBot 与网络层后真跑插件类，验证四件事——
  8 线程并发冷启动只解析一次房间；缓存为空时 `_where()` 不发请求；
  模拟 0.45 秒阻塞解析期间事件循环仍能推进心跳；解析失败不污染缓存、下次会重试。

## 十、安全设计

插件的行为边界很窄，下面逐项列出，便于审查与自查。

### 1. 网络：只有两个出网目标

| 目标 | 用途 |
| --- | --- |
| `https://pay.wxstc.cn/grdp-ele-third-unite` | 学校缴费平台的电费查询接口，唯一的业务请求 |
| `127.0.0.1:3000`、`127.0.0.1:3001`、`host.docker.internal:3000` | 本地 NapCat 的 HTTP 接口，仅发布消息时使用 |

除此之外没有任何地址：没有遥测、没有更新检查、没有 CDN、没有第三方统计。
NapCat 地址可用配置项 `napcat_url` 或环境变量 `NAPCAT_URL` / `NAPCAT_HTTP` 覆盖，
但只会连到你自己指定的地址。

### 2. 不做的操作

- 不执行 `eval` / `exec` / `__import__`，不反序列化 `pickle` / `marshal`；
- 不起子进程，不调 `os.system`，不需要 `sudo`（v3.0.0 已删除 `docker inspect` 探测）；
- 不读写 AstrBot 数据库，不修改模型上下文，不注册全局钩子；
- 除上述两个可选地址外，不读取任何环境变量。

### 3. 数据边界

插件写入的所有文件都在自己的数据目录
`data/plugin_data/astrbot_plugin_wxsc_elec_bill/` 下
（`notes.json` / `state.json` / `hist.json` / `export/`），
不碰插件目录之外的任何路径。

### 4. 下载接口防目录穿越

`/download` 只接受文件名：先 `os.path.basename()` 掐掉路径部分，再拼到 `export/` 下，
最后用 `os.path.isfile()` 确认存在才返回。`../`、绝对路径、软链接都取不到目录外的文件。

### 5. 日志

统一 `from astrbot.api import logger`，不把请求体、令牌或密钥写进日志。

`import logging` 只用于让 `_RingHandler` 继承 `logging.Handler`、使用 `logging.Formatter`；
不调用 `logging.basicConfig()`，不动 root logger，不设置全局级别，也不注册任何文件或网络 handler。

控制台的「运行日志」需要在进程内留一份副本，所以 v3.1.2 起给插件 logger 挂了一个
**只读的内存环形缓冲**（`_RingHandler`，最多 600 条）：只把已经产生的日志抄一份进内存，
不改日志级别、不写文件、不发网络请求；重载插件时先摘掉旧 handler 再挂新的，不会越积越多。

## 十二、隐私、风险与免责

### 1. 隐私

插件只读取缴费平台对**本房间**公开的余额与充值记录。充值记录中平台本身不返回姓名、
手机号或任何可识别信息，插件也不会去推断或收集。账号备注由使用者自行填写，仅存本地。

### 2. 接口风险（请务必读完）

`elec_core.py` 里的 `APPID`、`APPSECRET` 与那一对 RSA 密钥，是通过**分析该缴费平台
自己的微信小程序前端包**得到的——属于对该接口的逆向复刻，不是学校或平台授权下发的
开发者凭据。这意味着：

- **平台一旦轮换密钥或调整协议，插件会直接失效**，且不会提前通知。失效后需要按新版
  小程序前端重新提取，我无法保证能及时跟进；
- 平台若认定这类第三方调用违反其服务条款，可能封禁、限流或要求下线本插件；
- 所以**不要把本插件当作缴费或查询的唯一渠道**：金额与电量一律以平台页面显示为准，
  涉及欠费、退费、账目争议时，请以学校后勤或平台的正式记录为准。

### 3. 免责

本插件为个人自用工具，与无锡科技职业技术学院及该缴费平台**无隶属、合作或授权关系**，
亦未获其背书。使用者自行承担因使用本插件产生的风险；作者不对数据准确性、服务可用性
或由此引发的任何争议负责。若校方或平台方提出异议，本插件将立即停止维护并从各分发渠道
下架。
